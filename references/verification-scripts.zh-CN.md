# 验收脚本工程规范（13 条现场教训）

[English](verification-scripts.md) | [中文](verification-scripts.zh-CN.md)

> 适用对象：给单个工单写 `verify.sh` 的 PM / 工程师 / 验收方。
> 用法：写完脚本后逐条自查；**每一条都要能回答「什么情况下这脚本不合格」**。
> 这些规则来自真实项目里反复发生的现场事故——每一条都对应一次「检查本身失效」。

---

1. **改任何 `verify.sh` 的 AC 前，先把旧版存成 `verify.rev<N>.sh`**

   **规则**：只要改动既有脚本里的验收条件（增删 AC、放宽/收紧判据、改期望值），先在同一目录复制旧版为 `verify.rev<N>.sh`（`<N>` 递增，已存在则继续加一），新版头部写明「rev N，取代 rev N-1」；交付证据同时给出两版路径。这样第三方可以直接 `diff verify.rev1.sh verify.sh`，判断改动是修正还是放水。

   **违反长什么样**：就地 `vim verify.sh` 覆盖旧 AC；仓库里只剩最终版；验收方无法还原「改前到底查什么」。或者用 `git checkout` / 重写文件的方式抹掉旧判据，却在报告里声称「只是修正措辞」。

   **反例 / 证据来源**：一次修改验收标准时没有留副本，事后只能写 `evidence/ac-amendment-note.md` 承认旧版无法逐字复原；这使「合法纠错」与「降低标准」只能靠自述区分。

2. **回归断言禁止绑定「相对某个历史 commit 的变更范围」**

   **规则**：仓库级回归断言必须针对**当前 HEAD 的不变量**（文件存在、内容约束、链接可解析等），或把 baseline 作为显式参数（环境变量 / 命令行参数）传入。不要写死某个历史 commit 的 SHA 再断言 `git diff <历史 commit>..HEAD --name-only` 恰好等于某组文件；那种断言会被下一个工单的正常变更打破。

   **违反长什么样**：脚本里出现硬编码的 `git diff 3841fdd..HEAD --name-only`、`git diff 43b1056..HEAD` 并比较精确文件清单。下一个工单合法新增文件后，旧脚本必然报「范围不符」，但仓库并没有回归。

   **反例 / 证据来源**：某次工单 脚本在后续 HEAD 上现场复现 3 项假失败；某次工单 脚本在 2026-10-18 的 HEAD 上因范围断言与旧期望报 2 项 FAIL。两者都是历史 commit 绑定的直接后果。

3. **验收脚本不得扫描 `.delegate/` 等 gitignored 本地状态**

   **规则**：脚本只能检查 `git ls-files` 返回的受版本控制文件，或使用显式的受控文件清单；全仓扫描前必须排除 `.delegate/`、`node_modules/`、构建产物、缓存目录等本地状态。不要对整棵工作树做 `find`、`grep -r`、字数统计或链接检查而不加排除。

   **违反长什么样**：`find . -name '*.md'`、`grep -r ... .` 扫到 `.delegate/BACKLOG.md` 或验收方的临时日志；本地文档里的相对链接、字数、临时结论被当成仓库内容，导致「代码没动却 FAIL」。

   **反例 / 证据来源**：某次工单 的 Markdown 链接检查曾扫到 `.delegate/BACKLOG.md`，因本地文档链接而假 FAIL；这条规则要求脚本把扫描范围收窄到 tracked files，而不是相信「本地目录应该没问题」。

4. **脚本里的断言不得多于 spec 的 AC 表：每条断言都要能在 `TASK.md` 找到编号对应**

   **规则**：写脚本前先抄出 `TASK.md` 的 AC 表（ID + 一句话判据）。脚本里的每个检查都必须挂到其中一个 AC-ID 下；不允许“顺手多查一个”“上一单继承一个”的隐性断言。若确实需要新判据，先改 TASK 的 AC 表并留下修改记录，再写脚本。

   **违反长什么样**：TASK 只到 AC-8，脚本却打印 AC-9 / AC-5b 之类表外检查；或一个 AC 里塞进 TASK 没写的额外条件。越多表外断言，越容易出现与 spec 互斥的判据，且失败时无法归责。

   **反例 / 证据来源**：某次工单 的 AC-5b 是从旧单继承、未登记进 TASK 的断言，正是后来互斥冲突的根因。判不合格的方法：把脚本里所有断言的 ID 抽出来，与 TASK AC 表逐个比对，出现任一表外 ID 即不合格。

5. **TASK 与脚本的 AC 编号必须一一对应**

   **规则**：同一个 `AC-N` 在 TASK 与脚本中必须指同一件事；新增/删除 AC 时两边同一 commit 一起改，且尽量不要在中间插入导致后续编号整体漂移。交付报告里的「AC-N PASS」必须能同时对应到 TASK 表格行和脚本文本。

   **违反长什么样**：TASK 的 AC-7 是「无回归」，脚本的 AC-7 却是「文件计数」；或 TASK 的 AC-3 是「主题词」，脚本的 AC-3 是「范围」。这样「AC-8 PASS」会被误读成另一件事，验收记录失去可追溯性。

   **反例 / 证据来源**：某次工单 出现过 TASK AC-7 = 回归、脚本 AC-7 = 计数的错位，验收方据此误读通过项。判不合格的方法：并排打印 TASK AC 表与脚本 success/failure 文案，逐 ID 对照语义，而不是只比数量。

6. **负例断言写法纪律：写「禁止出现 X」前，先问「合格答案里会不会出现 X」**

   **规则**：负例断言必须证明「任何合格答案都不包含 X」；若合格答案可能为了解释、举例、引用而提到 X，就不能用全文件禁止。优先改成正例或结构断言；负例无法避免时，限定到具体命令/小节/代码块，并同时给出一个必须存在的正例作为反证。

   **违反长什么样**：spec 要求「说明如何配置 `--permission-mode`」，脚本却全文件禁止 `--permission-mode`；或要求「指出不要用 `bypassPermissions`」，脚本却禁止该词出现。合格答案一写就必然触发 FAIL，这就是互斥 AC。

   **反例 / 证据来源**：某次工单 AC-8、某次工单 AC-3 初版、某次工单 AC-5b 三次写出互斥 AC。判不合格的方法：拿一份按 spec 写的合格样例喂给脚本；若合格样例 FAIL，脚本即不合格。

7. **闸门强度：`grep -qF` 全文件子串匹配可被注释、同义词、说反话绕过**

   **规则**：关键断言不能只做全文件子串存在性检查。至少同时具备：(a) **命令行上下文锚定**（命中行必须包含调用命令/参数或位于指定代码块）；(b) **极性与邻近约束**（排除否定词，如「不要」「禁止」「错误示例」；限定同句/同行窗口）；(c) **变异测试**：至少构造一种「写进注释」「换成同义词」「说反话」的变异体，确认脚本对它报 FAIL。对每条关键 AC 记录变异命令与结果。

   **违反长什么样**：`grep -qF -- '--sandbox' file` 在 `<!-- --sandbox -->` 注释里通过；或文档写「不要使用 `--dangerously-bypass-approvals-and-sandbox`」也算命中；或把 `--sandbox` 换成同义的「沙箱开关关闭」后仍通过。闸门看似存在，实际对反向内容无感。

   **反例 / 证据来源**：某次工单 AC-4b 被「写进注释」现场绕过；某次工单 / 某次工单 的 AC-5b 用同义词与说反话的变异测试现场演示了词面匹配失效。判不合格的方法：对关键断言做至少一次反向变异，脚本仍 PASS 即不合格。

8. **长 flag 与短 flag 都要覆盖**

   **规则**：对每个受测 flag，先列出工具实际接受的全部写法（长形式与短形式），逐种断言；工具不支持某一种时，在脚本注释中写明依据。匹配短 flag 时必须加边界（前有行首/空白、后有空白/行尾），避免 `-a` 命中 `-abc` 或普通单词的一部分。

   **违反长什么样**：只 grep `--sandbox` / `--approval-mode`，漏掉 `-s` / `-a`；文档用 `-a never` 时脚本完全看不见。或者用 `grep -q -- '-a'` 误命中 `--allow`、`data` 等无关内容。

   **反例 / 证据来源**：某次工单 的 `-a never` 表述修正说明短 flag 在真实文档里会被使用；只查 `--` 的脚本会漏。判不合格的方法：把受测命令改写成短 flag 形式喂给脚本，脚本仍 PASS 即不合格。

9. **位置敏感的 flag（顶层 vs 子命令）必须做位置感知校验**

   **规则**：对「只能放在顶层」或「只能放在子命令后」的 flag，不能只查存在性。脚本要解析命令 token，确定子命令出现的位置，再断言 flag 位于其允许的一侧；最好对正例与错位反例各跑一次。多级子命令（如 `codex exec resume`）要按实际层级判定。

   **违反长什么样**：`grep -q -- '--sandbox'` 在 `codex exec --sandbox ... resume` 这种错位写法上也 PASS；而该 flag 在错误位置会被 CLI 忽略或拒绝。存在性检查把「写到了」误判为「写对了」。

   **反例 / 证据来源**：某次工单 发现「顶层 `codex resume` 是交互式 picker、非交互要用 `codex exec resume`」，同一 flag 在不同位置语义不同；只做存在性检查无法区分。判不合格的方法：把 flag 移到错误位置，脚本仍 PASS 即不合格。

10. **证据类断言要检查「是不是真在命令链里」，不能只看关键词出现过**

    **规则**：验收证据必须能看出「执行了什么命令 + 带什么参数 + 得到什么输出/退出码」属于同一次调用。断言应要求同一代码块或同一命令链里同时出现命令、关键参数与结果标记（输出片段 / exit code），而不是在整份日志里分别找到这些词。外层包装器的 exit 0 不能作为内层命令成功的证据。

    **违反长什么样**：日志里出现 `codex exec` 和 `exit 0`，但 `exit 0` 来自外层 `claude -p`，内层命令实际全部被拒；或证据只有一句「已运行」，没有命令行、输出与退出码。关键词 grep 全绿，事实没有发生。

    **反例 / 证据来源**：某次工单 候选条目记录的真实事故：`claude -p` 外层 exit 0 而内部命令全被拒；另有多次验收因证据只有结论、没有命令链而判「读不到」。判不合格的方法：删掉输出/退出码只留命令名，脚本仍 PASS 即不合格。

11. **验收方产出与日志一律写主仓库绝对路径；删除 worktree 前必须先收证据**

    **规则**：验收简报和脚本中的证据落点必须是主仓库的**绝对路径**（例如 `/Users/.../repo/.delegate/<ID>/evidence/...`），不得使用相对路径或 worktree 内的路径；若必须在 worktree 工作，结束前先把 verdict、日志、截图复制到主仓库，并用 `test -s` 逐个确认存在，再执行 `git worktree remove --force`。

    **违反长什么样**：简报写「产出到 `evidence/verdict.md`」，验收方在 worktree 内写文件；随后 worktree 被强制删除，verdict 与日志一起消失。或证据写进 `/tmp`，换机器/清理后无法复核。

    **反例 / 证据来源**：某次工单 曾因删除 worktree 丢失 verdict 与日志，靠二次落盘才补救；某次工单 / 某次工单 / 某次工单 / 某次工单 四次出现验收方「读不到」工程师证据，根因都是落点问题。判不合格的方法：`grep` 简报中的每个证据路径，出现非绝对路径即不合格。

12. **`verify.sh` 是一次性工单脚本；长期回归必须另建独立于工单的套件**

    **规则**：每个工单的 `verify.sh` 只对该工单的 baseline + spec 有效，交付后归档，不再假设它在未来 HEAD 上仍然全绿。需要长期回归时，另建一套受版本控制、参数化、只依赖当前 HEAD 不变量的回归套件（例如 `tests/` 或 CI 配置），并明确哪些检查属于套件、哪些属于工单。工单脚本不得被其他工单或 CI 直接调用。

    **违反长什么样**：把 `.delegate/某次工单/verify.sh` 挂进 CI 或新工单的验收命令；或在下一个工单里直接复用旧脚本而不检查其历史 commit 绑定断言，于是旧脚本的预期假失败被当成真实回归。

    **反例 / 证据来源**：某次工单 脚本在今天的 HEAD 上因范围断言与被 某次工单 有意推翻的旧断言报 2 项 FAIL——这是预期假失败，不是仓库回归。判不合格的方法：在新 HEAD 上运行旧工单脚本并得到 FAIL，不能据此判回归；若 CI 引用了工单脚本，该 CI 配置即不合格。

13. **禁止精确计数断言（「恰有 N 个」），除非该目录确实封闭**

    **规则**：不要用 `-eq` 断言受控目录里的文件/条目「恰好 N 个」，除非该目录在工单生命周期内确实封闭、不会随其他工单合法增长。需要防止文件缺失时，逐个列出必须存在的文件并检查非空（存在性断言）；文件总数只作下界（`-ge`）或仅打印实际值，不写成判据。

    **违反长什么样**：`[ "$actual_refs" -eq 6 ]` 或 `[ "$actual_platforms" -eq 3 ]`。下一个工单合法新增一份文档或一个平台文件后，目录数量从 6 变 7、从 3 变 4，旧脚本立刻报「数量不符」；仓库本身没有回归，这是新增合法文件造成的假失败。

    **反例 / 证据来源**：一次真实翻车（`references` 的 `-eq 6`：某次工单 新增第 7 个文件即 FAIL，改为下界）；一处同类未爆地雷（`platforms` 的 `-eq 3`，某次工单 rev4 提前修复）。判不合格的方法：在受检目录新增一个合法文件后重跑脚本，若出现计数类 FAIL 即不合格。
