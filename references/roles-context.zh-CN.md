# 角色、上下文和观察状态

[English](roles-context.md) | [中文](roles-context.zh-CN.md)

角色由 PM 派发的职责决定。工具、进程、厂商、模型和房间工位分别记录，不能互相替代。

## 谁做什么

| 角色 | 职责 | 上下文 |
|---|---|---|
| 老板 | 提供意图、反馈和优先级，决定是否接受结果 | 与 PM 自然对话 |
| PM | 澄清需求、派发、收结果、向老板报告 | 保留项目决策；自检不能冒充独立验收 |
| 工程师 | 实现、调试、自测、返工、交付 | 同一实现链路持续保留；默认续接明确的工程师会话 |
| 验收员 | 独立检查指定交付版本，给出证据和结论 | 每轮正式验收另开全新上下文；不继承 PM 或工程师聊天 |
| 记录员 | 提取想法、约束、决定、反馈，与 PM 已有记录合并 | 用原始记录核对来源，不决定验收通过或擅自改全局技能 |

“全新上下文”不是不给验收员资料。它需要需求、约束、验收标准、基线、交付版本和必要的环境说明。
不要把实现者的试错聊天、辩解或自评作为验收前提。
不同模型可以交叉检查，但换模型本身不能证明独立。

## 工程师如何续接

第一次实施可以建立新会话；后续同一任务默认续同一个明确 ID，连同其工作区和已排除方案一起保留。
恢复前先确认原执行者已完成或停止，避免两个写入者修改同一工作区。
不要用 `resume --last` 猜是哪一个工程师。

工程师换人、宿主不支持续接、或上下文确实需要换班时，才写最小交接。记录原会话、交接去向、版本、未完成项和必要证据。
同一工程师正常继续工作时，更新已有状态即可，不为每个步骤另造交接文档。
保留工程师上下文不影响验收独立性；隔离的是验收员与实现讨论。

## 验收如何保持独立

- 派发记录须写明 `role=verifier`、`context_policy=fresh`、新会话 ID 和待验收版本。
- 新验收会话不能是工程师会话、PM 会话或它们的 fork。只改角色名不成立。
- 验收员在独立快照重跑检查；可在允许的临时输出目录准备依赖、构建和运行测试，不改交付源码、锁文件、测试或需求。
- 验收失败回到原工程师修复。修复后的正式复验使用新验收上下文；原验收员可以澄清其证据，但不能代替新版本的正式复验。
- 宿主只能提供声明、不能证明上下文隔离时，应写明限制。声明不是密码学证明。

## 派发记录与观察窗

复用运行记录，给每次派发关联 `task_id`、`role`、`owner_session`、`context_policy`、工程师上下文链、真实 `job_id/agent_id` 和目标版本。
这些信息随启动记录生成，不要求老板填写新表。

角色登记只说明“这次派发承担什么职责”。启动、运行、结束必须另外核对宿主事件或受管执行回执。

| 实际发生的事 | 观察窗显示 |
|---|---|
| PM 自己读文件、构建、自检 | PM 工作；不凭空增加工程师 |
| 已登记工程师启动/续接/测试 | 原工位工程师工作；测试仍属于工程师 |
| 工程师进程成功结束 | 实现已交付、待派验收；验收员尚未进场 |
| 新上下文验收派发实际启动 | 验收员进场，绑定被检查版本 |
| 验收任务退出 | 验收任务结束；没有明确结论时不显示 PASS |
| 验收 FAIL / PASS | 分别显示返工 / 验收通过待 PM 汇报；不是自动获得老板接受 |
| PM 真的提出待回答问题 | 仅对应房间出现问号；回答或撤回后清除 |
| 记录员实际开始/结束 | 临时进场/离场；仅在实际任务期间显示 |
| 无匹配派发、连接过期、事件缺失 | 显示“状态未知”；不猜角色、不冒充完成或空闲 |

普通后台命令、调查任务、测试辅助程序不自动成为工程师或验收员。
同一个子代理工具可以承载不同职责；不同 CLI 也可以承载同一种职责。

## 保留既有体验

一个激活的项目一间房，项目 ID 稳定。闲置房间调暗；未知状态要标明。
白天、黄昏、夜晚继续由本地时钟驱动。
纸箱只统计该项目当天实际使用的技能，重复调用只算一次；目录存在不算使用证据。
观察窗默认随技能启动，不抢焦点，用户要求关闭就关闭。显示失败不能阻止项目工作。

## 记录如何反哺

记录员按自然语言提取待讨论想法、规格、决定和反馈，保留来源与不确定性。
PM 盘点全部记录，在合适的收尾时机或老板询问时，报告已落实、待处理和待核实事项。
讨论过、提交存在、文档命中都不等于功能完成，完成状态必须有对应行为/交付证据。
新方法先在项目内试用；是否升级全局技能留到项目复盘。规则过度时，PM 用记录和实际收益判断保留、重写或删除，不靠固定次数决定。
